### <a name="_qmphm5d6rvi3"></a>**Решение**
При выборе решения я руководствовался в первую очередь необоходимостью сделать наиболее дешевое из возможных решений с учетом требований по доступности.

Основной проблемой существующей системы является проблема горизонтального масштабирования базы данных АБС и отказ всех услуг при недоступности базы данных АБС.

Чтобы эту проблему решить предлагается расширить используемый функционал CRM. Сейчас система используется только кол-центром. CRM может взять на себя функции обработки заявок без участия кол-центра.

Чтобы разгрузить базу данных АБС так же необходимо создать новый микросервис, который будет отвечать только за депозиты. Это сервис будет кэшировать ставки по депозитам. В нем же будет реализована логика по работе с депозитными продуктами, которая сейчас написана на PL/sql.
Таким образом, база данных будет использоваться только для dml операций.

Так как в команде есть разработчики, владеющие spring boot и уже есть система CRM на spring boot в качестве технологии был выбран spring boot.

Между crm и новым сервисом поставим брокер kafka, как рекомендуется. Таким образом мы отвязываем CRM от АБС. CRM сможет работать с заявками при недоступности АБС. У АБС появится возможность перечитать kafka при недоступности своей БД.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**
Переписать всю АБС с использованием актуальных технологий - долго, дорого, можно не решить бизнес-задачи.

Сделать автоматическое открытие депозитов - пока бизнес не требует.

Настроить централизованный сбор логов и мониторинг - можно будет реализовать позже.

Выделить микросервис в интернет-банке для обработки депозитов - будет обходное решение для открытия депозитов в виде сайта. Работу с заявками можно переложить на CRM.

**Недостатки, ограничения, риски**

Дублирование логики в новом сервисе и хранимых процедурах БД АБС. На этапе миграции с хранимых процедур потребуется поддерживать одинаковую логику в двух местах.

Статусная модель в заявке неполная. После отправки в CRM она остается в последнем статусе и не понятно, выполнена она до конца или не выполнена.

Возможно дублирование заявок, потребуется уделить внимание вопросу идемпотентности.

Отсутствие централизованного логирования и мониторинга. Сложно обнаружить сбой.
